# `/data-products` — User guide

## What it does

The Data Products tab lists every analysis output the worm has generated as
a **first-class artifact** — chart, table, board-deck breakdown, anomaly
report, retention cohort, runway model, recurring summary. Not a
one-shot chat reply: a tracked, replayable artifact with full provenance
and consumption trace.

Each row carries: name, kind (chart / table / report / notebook),
requested_by Person, owner domain, generated_at timestamp, source-hash
count, consumption count, freshness badge (green ≤ 7d, amber ≤ 30d, red
older), and a Replay button.

Every role has this tab as a daily-or-weekly surface.

## First action

Trigger an artifact via chat:

1. In a connected channel, mention the worm: `@WormBase what's our Q3 net
   revenue?`
2. Within ~3-5 seconds the worm replies with a sourced answer + a link
   like `data-product:q3-net-rev-2026-04-28`.
3. Open `/data-products`. The new row is at the top, status `generated`.
4. Click the row. The drawer renders the artifact (HTML for charts and
   reports, table view for raw data) with **source hashes pinned** below.

To replay:

1. With the row drawer open, click **Replay**. The orchestrator
   regenerates the artifact against the same pinned source-hashes.
2. UI shows **✓ bit-identical content_hash** — the regenerated bytes match
   the original hash. This is the C2 deterministic-output proof.

To author from scratch:

1. Click **New data product** in the header.
2. Pick kind, source(s), parameters. Submit. Writes
   `emit_data_product_proposed`. The worm's data-product orchestrator
   generates within ~10s; status flips to `generated`.

## Advanced

- **Filter by kind / status / domain / person** — URL-driven chips at the
  top. Combine to narrow ("show me every retention chart Carol consumed
  this month").
- **Bulk archive** (admin-only) — writes `emit_data_product_archived` for
  each. The artifacts stay in S3 and the bronze provenance stays in the
  ledger; only the row hides.
- **Re-run on schedule** — open a data product → **Schedule** → pick a
  cadence. Writes `emit_data_product_proposed` with `recurrence=weekly`
  (or daily / monthly). The worm regenerates on schedule.
- **Cite from a decision** — every Decision row has an "Add citation"
  button that pins a data product. Writes `emit_data_product_consumed`
  with `surface=decision`. Auditors trace decision → artifact → source
  bytes.
- **Per-Person data product activity** — open `/people/{id}`; the
  drill-in has "Data products requested" + "Data products consumed"
  sections.
- **Per-domain freshness roster** — `/domains/{id}` shows every artifact
  in this domain with a freshness badge. Admins click stale ones to
  re-run.

## Behind the scenes

Reads from `projection_data_products` + `projection_data_product_runs` +
`projection_data_product_consumption`, folds of:

```
emit_data_product_proposed     (chat / form / autoresearch)
emit_data_product_generated    (orchestrator finished; bytes in S3)
emit_data_product_consumed     (every view / share / cite event)
emit_data_product_archived
```

Artifact bytes live in S3 (LocalStack in dev, real S3 in prod) at
`s3://${bucket}/${tenant_id}/data-products/${data_product_id}/${run_id}.${ext}`.
The ledger carries `contents_uri` + `content_hash`; never the bytes.

The replay orchestrator
(`apps/worm-core/src/wormbase_core/data_product_actions.py`
→ `replay_data_product`) re-runs the same generation logic against the
pinned source-hashes; if any source's bytes have changed (hash mismatch),
the run is flagged "source drift" and a new artifact is generated with a
new ID — the old one stays accessible.

## Why first-class

This closes a gap the older PRD §10 demo arc had: Carol's "what's our Q3
net revenue?" question used to produce a chat receipt and nothing the
user could come back to, drill into, or share with a board member. With
this surface, the answer becomes an artifact at
`s3://wormbase/{tenant}/data-products/{id}/{run_id}.html`, addressable
from `/data-products`, citable in audits, replayable from pinned
source-hashes.

The principle (per `feedback_data_products_first_class.md`): every
analysis output is a ledger-tracked artifact, **not a transient chat
reply**.

## Failure modes

| Symptom | Cause | Fix |
|---|---|---|
| Replay fails with `source_drift` | A source has been re-bronzed since last run | Decide: re-run with new bytes (new artifact, new id) or restore old bronze hash |
| Generation hangs | Kernel state too large; memory cap exceeded | Cancel via drawer; reduce input scope; retry |
| Empty state after chat answer | Worm answered but didn't promote to data product | Ask an admin to enable `auto_promote_chat_answers=true` in `/settings` |
| Artifact 500s on render | S3 unreachable | `make logs localstack`; restart |
| Consumption count stuck at zero | Tracking disabled in the renderer (legacy artifact) | Re-run via Replay button to refresh the consumption hooks |
